# r3-i18n: Arabic / English interface, RTL, locale-safe GxP formatting (roadmap M38)

Release R3. My changes are not committed; the wave gate commits them. Wiring in files this track does not own is in
`docs/changes/r3-i18n.gate.patch` (see "For the gate").

## What changed

* **i18n layer** (`src/i18n/`, no dependency): `en.json` (source) and `ar.json` (DRAFT), `translate.ts` (pure `translate`, `{placeholder}`s,
  English fallback, key shown if missing everywhere), `store.ts` (language + digit style, localStorage guarded, sets `<html lang dir data-digits>`),
  `index.ts` (`t`, `useLang`, `localizedError`), `preferences.ts` (server sync), `LanguageSwitch.tsx` (header and sign-in screen; in Arabic a
  second control picks display digits).
* **Server-side preference**: migration `0350_i18n_preferences` (sidecar table `user_preferences`, users untouched), `GET/PUT /api/me/preferences`
  (`src/i18n/server/`): strict zod, actor from `req.user`, optimistic version check, audit entry (entity `UserPreference`) in the same
  transaction. After sign-in the server choice replaces the local one; a choice made on the sign-in screen is saved on first sign-in.
  Display only: the language never changes a stored value (test: an Arabic-interface analyst's result is stored `99.5`).
* **RTL**: all physical utilities in the owned components converted to logical ones (ml/mr/pl/pr/left/right/text-left/right/border-l/r/rounded-*;
  165 lines), directional icons flip (`rtl:-scale-x-100`), ids/batches/hashes/versions in `<bdi dir="ltr">`, result and code inputs `dir="ltr"`,
  charts `dir="ltr"`, letter-spacing off for Arabic (it breaks joining). Static test fails on any physical utility.
* **Font**: Noto Sans Arabic 400/600/700, Arabic subset, woff2, **152 KB in total**, SIL OFL 1.1 (licence text bundled in
  `src/i18n/fonts/`), from @fontsource/noto-sans-arabic 5.3.0, local asset (works offline). Declared with `unicode-range`: an English session
  never fetches it.
* **Formatting** (`src/lib/format.ts`): `13 Oct 2026, 12:12:00 GMT+3` (Gregorian, month as a Latin word, offset always shown, identical in both
  languages, fixed `en-US`/`latn`/`gregory`, never the OS locale); `formatDate` for bare dates is not shifted by the time zone; Arabic-Indic digits
  are a DISPLAY option only (`exportTimestamp` ISO UTC, `exportNumber`, `printDateTime` ignore it); `parseResultInput` refuses `1,5` and `1,234.5`,
  reads `١٫٥` as `1.5` and tells the user. All 38 `toLocale*` calls in the owned components are gone (a static test keeps it so).
* **Server stays authoritative for typed results**: unchanged `parseDecimal` (r1); tested through the real API: `99,5`, `99٫5٬0`, `1,234.5`, `9.9e1`, `٩٩,٥` are 400 and
  change nothing, `٩٩٫٥` is stored `99.5`. The result grid shows the comma refusal before saving.

## PDFs

Measured, not assumed: jsPDF with Helvetica prints Arabic as garbage; with an embedded TTF and `lang: 'ar'` a pure-Arabic line is shaped and ordered correctly, but a line mixing Arabic and Latin/numbers is not
(the Arabic-only font has no Latin glyphs and the line vanished). A reliable result needs Chromium `printToPDF` (the roadmap design). **CoA and reports therefore stay in English with UTC
timestamps**, and the CoA panel says so in Arabic. Existing issue (not caused here): Arabic master data (a product name) printed in jsPDF PDFs comes out garbled.

## Decisions for the user

* **The Arabic catalogue is a machine-assisted DRAFT.** QA and a linguist must approve it before use in a regulated process; the switch labels it (مسودة).
* Regulated wording (signature meanings, record/sample states, OOS/Pass, report titles, audit text) is deliberately NOT translated; QA must decide a glossary first.
* Dates print with Latin month abbreviations in Arabic too (unambiguous, identical). Confirm or choose Arabic month names for screens only.
* Default display digits are Latin; Arabic-Indic is opt-in.
* A comma in a result is refused, not interpreted. Confirm that no site uses comma decimals.
